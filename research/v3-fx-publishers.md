## 2. ECB euro reference rates — detail

Sources: ECB page [V-2nd] https://www.ecb.europa.eu/stats/policy_and_exchange_rates/euro_reference_exchange_rates/html/index.en.html ; Framework PDF (23 Jun 2026) [V] https://www.ecb.europa.eu/stats/pdf/exchange/Frameworkfortheeuroforeignexchangereferencerates.en.pdf ; 2015 press release [V] https://www.ecb.europa.eu/press/pr/date/2015/html/pr151207.en.html ; Banca d'Italia (2nd) [V] https://www.bancaditalia.it/compiti/operazioni-cambi/cambi/index.html?com.dotmarketing.htmlpage.language=1 ; disclaimer/copyright [V] https://www.ecb.europa.eu/services/using-our-site/disclaimer/html/index.en.html ; API docs [V] https://data.ecb.europa.eu/help/api/data ; TARGET closing days [V] https://www.ecb.europa.eu/press/pr/date/2000/html/pr001214_4.en.html and https://www.ecb.europa.eu/ecb/contacts/working-hours/html/index.en.html

- **Fixing**: "based on the daily concertation procedure between central banks across Europe, which normally takes place around 14:10 CET" (ECB page). Framework: "determined by the ECB daily around 14:10 CET between the administrator and the calculation agents". The 2015 release: "point-in-time snapshot at 14:15 CET". SDMX `TITLE_COMPL` still reads "2.15 pm (C.E.T.)". **[I]** 14:10 is the current wording; the ticket's "14:15" is the legacy one — same five minutes either way.
- **Definition**: "no solicitation process … by a panel or by polling"; transactional data where liquid, else "predominantly or exclusively on bid and offer rates"; for quote-based currencies "the rates are set at the mid (arithmetic average) of the bid and ask quotes observed" (Framework). Named list of participating central banks **[NF]**.
- **Publication lag**: "usually updated at around 16:00 CET" (ECB page); moved from 14:30 to 16:00 on 2016-07-01 to "reinforce the distinction between exchange rate fixings used as benchmarks for transaction purposes and the ECB reference rates that are published for information purposes only" (2015 release). Observed `eurofxref-hist.csv` zip timestamp 15:56 CET on 2026-10-12 [V-obs].
- **Coverage**: `eurofxref-daily.xml` on 2026-10-13 (data 2026-10-12): `BRL 5.5819`, `CNY 7.4832`, `INR 107.0860`, `ZAR 18.4945`, `USD 1.1181` — 29 currencies; BGN gone (euro adoption 2026-01-01); RUB last published 2022-03-01 [V].
- **Endpoints verified by fetch (HTTP 200)**: `eurofxref-daily.xml` (gesmes XML, one `<Cube time=…>` with per-currency `<Cube currency= rate=>`), `eurofxref-hist-90d.xml`, `eurofxref.zip` (long-form dates, trailing comma), `eurofxref-hist.zip` → `eurofxref-hist.csv` (ISO dates, `N/A` for discontinued, history to 1999), SDMX REST `https://data-api.ecb.europa.eu/service/data/EXR/D.USD.EUR.SP00.A?lastNObservations=3&format=csvdata` (CSV header includes `TIME_PERIOD,OBS_VALUE,OBS_STATUS,…,DECIMALS,…,TITLE_COMPL`); OR-syntax `D.BRL+CNY+INR+ZAR.EUR.SP00.A` works; default format without `format=` is SDMX-ML 2.1 GenericData. Parameters: `startPeriod endPeriod updatedAfter firstNObservations lastNObservations detail includeHistory`. Rate limits **[NF]**.
- **Terms**: "users of this website may make free use of the information obtained directly from it subject to the following conditions: When such information is distributed or reproduced, it must appear accurately and the ECB must be cited as the source … If the information is modified by the user … this must be stated explicitly." Liability disclaimer covers the reference rates explicitly. **[I]** A USD cross derived from two ECB legs is a "modification": label it derived, cite ECB.
- **Deriving USD crosses**: USD/BRL = EURBRL ÷ EURUSD etc. Both legs are the same concertation instant, so the cross is a same-time mid. Framework §2.2/2.5: for currencies "that are traded in market hours that do not overlap with the time of the concertation" the USD cross "should be the baseline scenario" — **[I]** the ECB's EUR rate for BRL/CNY/INR/ZAR is itself most likely built from a USD cross, so dividing recovers it up to rounding. ECB guidance to *users* on triangulation **[NF]**; academic note on the error **[NF]**. Rounding: ECB page says four decimal places, but the SDMX `DECIMALS` attribute varies per currency (JPY 2, CZK 3, GBP 5); BRL/CNY/INR/ZAR/USD are 4 dp. My arithmetic (not an ECB figure): relative rounding error ≤ 0.5×10⁻⁴/rate → USD 4.5e-5, BRL 9e-6, CNY 7e-6, INR 5e-7, ZAR 3e-6; a derived USD cross carries ≤ ~5e-5 relative error — ~1 USD/MT on a 20,000 USD/MT cargo value, negligible against any sensible economic threshold.
- **Holidays**: no rate on TARGET closing days — 2026: 1 Jan, 3 Apr, 6 Apr, 1 May, 25 Dec, 26 Dec [V]. Note the ECB *does* publish on Brazilian/Chinese/Indian/South African holidays (2026-10-12 BRL published while BCB had no PTAX) — a date-mismatch class the verifier must label, not compare.

## 4. What Yahoo's `XXXUSD=X` close is

Sources: Yahoo providers table [V] https://help.yahoo.com/kb/finance-for-web/exchanges-data-providers-yahoo-finance-sln2310.html ; quote page [V] https://finance.yahoo.com/quote/BRLUSD=X/ ; chart API [V-obs] `https://query1.finance.yahoo.com/v8/finance/chart/BRLUSD=X?range=5d&interval=1d` ; yfinance issues [V] https://github.com/ranaroussi/yfinance/issues/1071 , https://github.com/ranaroussi/yfinance/issues/2451 ; https://github.com/eminsk/yfinance-ta-patterns/issues/12 ; https://github.com/alfwro13/Stock_Analysis_Project/pull/231

- **Provider**: "Currency Rates · =X · Real-time · ICE Data Services" (help table); quote page says "CCY - Delayed Quote". Price type (bid/mid/indicative) **[NF]** — Yahoo publishes none.
- **Bar boundary — load-bearing finding, verified twice (subagent and me, 2026-10-13 13:44 UTC)**: chart metadata `exchangeName: CCY`, `exchangeTimezoneName: Europe/London`, `gmtoffset: 3600`, `currentTradingPeriod.regular` = 2026-10-12 23:00:00 UTC → 2026-10-13 22:59:00 UTC (`BST`). Completed daily bars are stamped 23:00 UTC (= 00:00 London). The in-progress bar carries `Close: null` until London midnight. **[I]** Yahoo's FX "Close" for date D is the last ICE tick before **00:00 London on D+1**, i.e. 19:00 ET (summer) / 19:00 EST (winter, 00:00 GMT) — **not 17:00 New York**, which is asserted only by third parties, never by Yahoo.
  - **Consequence for this repo (not fixed here, needs its own ticket)**: `FX_SESSION_CLOSE_LOCAL = (17, 0)` New York accepts a bar as finished from 21:00/22:00 UTC, but Yahoo keeps writing it until 23:00/00:00 UTC. The 21:30 UTC `refresh-prices.yml` slot (LAYERS.md: "lands after the FX close") therefore stores a bar with 1.5–2.5 hours still to run, and the ~20:00–24:00 UTC deploy landings are split. Hypothesis to test in the prototype ticket: re-pull Yahoo for a stored FX row the next day and diff Close — if it moves, this is the mechanism behind the #447 revisions. Alternative explanation to rule out: ICE back-corrections unrelated to the bar boundary (the #447 revisions were *days* later, which the boundary alone does not explain).
- **Data quality**: Open==Close on daily FX bars (yfinance #1071, maintainer: "this is what Yahoo has on their website so nothing we can do"; closed not-planned); eminsk #12: "median candle body … ~0 to 1 pip, while the median candle range … 50 to 130 pips"; holiday repeat (CNY, §3); `USDBRL=X` bar 2026-10-04: O 5.2241 H 5.2244 **L 4.9548** C 5.2231 — a 5% low against an unchanged close, looks like a bad tick [V-obs]. Close outside High/Low on `=X` externally **[NF]**; this repo's #447 is the only evidence.
- **Inverse pairs**: `BRLUSD=X` Close 0.19145717 vs 1/`USDBRL=X` 5.2231002 = 0.19145717 — reciprocal to ~1e-6 % with identical `regularMarketTime` [V-obs]; non-reciprocity only appears after 4-dp display rounding.

## 5. Expected explained-discrepancy band: ECB 14:10 CET vs Yahoo London-midnight close

Gap: 14:10 CET → 00:00 London next day = **~10 h 50 m** both seasons (summer 12:10 → 23:00 UTC; winter 13:10 → 00:00 UTC), spanning the London/NY overlap — the highest-volatility hours of the day. The ticket's "~8 h" (assuming 17:00 NY) understates it.

Evidence found (quoted, not estimated):
- Andersen & Bollerslev (1997, J. Empirical Finance 4:115–158), DM/USD 5-min Reuters quote midpoints, Oct 1992–Sep 1993 [V]: return std dev **hourly 0.148 %**, 2-h 0.212 %, 4-h 0.300 %, **8-h 0.423 %**, 12-h 0.520 %; intraday average absolute 5-min returns "from a low of around 0.01% at 04.00 GMT … to a high of around 0.05% at 15.00 GMT". https://finance.martinsewell.com/stylized-facts/volatility/AndersenBollerslev1997b.pdf (2nd: https://public.econ.duke.edu/~boller/Published_Papers/jf_98.pdf). A major, 30 years old — a floor, not a band for BRL.
- EM intraday hourly σ for BRL/ZAR/INR/CNY from BIS/central-bank papers: **[NF]** (BCB WP 297 exists but gives no numbers in the abstract; BIS QR Dec 2022 has none).

## 7. Recommendation — Tier 1 vs Tier 2 per pair for the accuracy ledger

Glossary (#472 / CONTEXT.md): Tier 1 = publisher of record; Tier 2 = second provider, *same definition*; Tier 3 = recomputation. Observation: **no Tier 1 candidate shares Yahoo's definition** (a London-midnight ICE indicative close). Every CB fixing differs in time and construction, so each per-pair check is a *different-definition* comparison that needs a labelled explained band; the ECB cross is the only source that covers all four pairs at one instant, free, redistributable with citation. The ticket's framing — "ECB is Tier 2" — should be sharpened: the ECB cross is a Tier 2 *provider* but not the *same definition*; call it the operative verifier and state the time gap on the ledger row.

| Pair | Tier 1 (publisher of record) | Tier 2 (operative verifier) | Third / retrospective | Notes |
|---|---|---|---|---|
| **BRL** | **BCB PTAX fechamento** — real fixing, free JSON, ODbL. Compare Yahoo close vs PTAX venda *and* compra (bid/ask spread 0.0006 on 9 Oct) → use mid; gap ~7 h to London midnight | ECB EURBRL/EURUSD cross, 14:10 CET (~2 h before PTAX's last poll) | FRED DEXBZUS (noon NY, weekly) | Date mismatch on Brazilian holidays (PTAX absent, ECB/Yahoo present) must label, not compare. **Verdict: Tier 1 + Tier 2 both free and publishable.** |
| **CNY** | CFETS central parity — *pre-open* fixing 01:15 UTC, ±2% band by construction, licence forbids storing/publishing | **ECB cross** at 14:10 CET = 20:10 Beijing (onshore still trading to 03:00) — closest free, publishable comparator | FRED DEXCHUS (weekly) | Parity vs close is a definitional gap, not a time-of-day one: use CFETS as **pass/fail + delta only** (A18 convention) with a wide band, or drop it and let the ECB cross carry the stratum. Cross-cutting:
1. **Fetch ECB once** (`eurofxref-daily.xml` for the edition, `eurofxref-hist.zip` for backfill; SDMX for the verifier script, which must share no code with `fetchers/`). Label every derived cross "derived from ECB EUR reference rates, 14:10 CET concertation; ECB cited; modification stated" to satisfy the ECB copyright condition.
2. **Record the time gap on the ledger row**: Yahoo close is London midnight; the explained band is a ~11-hour move, not ~8. Decide tolerances from a 60-day empirical pull in the prototype ticket, seeded with the §5 hypotheses; treat "fixing inside the day's H–L" as the volatile-day rule.
3. **Open a defect ticket for the FX session guard**: `FX_SESSION_CLOSE_LOCAL = (17, 0)` New York does not match Yahoo's observed London-day bar; the 21:30 UTC fast refresh stores an unfinished FX bar. Not in scope of this research — but it is a wrong-number mechanism (invariant 11) affecting every `home_per_mt` leg.
4. **FRED H.10** is free, public-domain and in the existing FRED fetcher's reach (same key): add DEXBZUS/DEXCHUS/DEXINUS/DEXSFUS as the retrospective third source for the weekly sample, never for a current edition.
5. **Licence gates (invariant 9)**: CFETS, FBIL and SARB texts all restrict redistribution; PTAX (ODbL), ECB (cite + state modification) and H.10 (public domain) do not. Only the latter three may ever show a verifying *value* on the public ledger page.
